## 1. Agentix：调度优化如何被时间线解释（R10 三模型总结）

来源：[agentix_autotrace/R10_SUMMARY.html](agentix_autotrace/R10_SUMMARY.html)（原路径 `/data3/Projects/AgentSys/artifacts/agentix_8b/autotrace/`）

### 1.1 实验设置
- 负载：25 个 program（bfcl 8 / sharegpt 5 / lats 12），共 2,440 个 call，约 1.5 万 step/捕获；同负载同栈，唯一变量是调度策略（FCFS vs agentix_core）。
- 模型：LLaMA-3.1-8B、Qwen3-1.7B、Qwen2.5-VL-3B；cap=16、0.5 program/s 制造排队。
- 本实现：进程表放在客户端 serving 适配层，每 program 维护 {attained_us, wait_us}，按程序累计服务时间（PLAS）入 K=4 级 MLFQ（入队界 [0,2,8,32] s，量子 32/64/128/256 token），vLLM 0.29 原生 priority 调度接入；ATLAS（多线程关键路径）已实现。
- Process 层级已在 A00 守恒门下三方对齐（规格 = 运行记录 = trace）：program → call → step → scope。

### 1.2 三视图结论

| 视图 | 回答的问题 | 结论 |
|---|---|---|
| 端到端 process 时间线 | 优化生效了吗 | 短程序车道的红段（等待）消失、lats 车道不变。30 s 窗内短程序等待合计：LLaMA 63.8 s→6.4 s（-90%），VL 19.7→2.1 s（-89%），Qwen3 4.5→1.4 s（-68%）。同一 call p00017#15：等待 3,821 ms→158 ms，服务段 1,408 vs 1,402 ms 不变。 |
| 高延迟 process 时间线 | 提升多少 | 服务侧不变 ⇒ 用等待几何量重放得**上界**：LLaMA 2.05× / VL 1.46× / Qwen3 1.14×；**实测** mean 1.33× / 1.09× / 0.99×，p90 1.86× / 1.15× / 1.11×，均落在 1×–上界之间且长尾更接近上界。重 forward step 堆两侧同形（LLaMA 45.1 vs 47.4 s）。 |
| 并发 process 时间线 | 为什么 | 两侧顶着同一面资源墙：突发内 NCU 中位 L2≈76%、SM/tensor≈49%、DRAM 14–20%；最忙 300 ms 内 GPU busy 也只有 18–25%，突发间是 host 调度空隙。资源与并发两个自由度都被排除后，收益只能来自 call→step 排序。above-cap 时长与 p90 提升单调：169 s→1.86×，77 s→1.15×，40 s→1.11×。 |

### 1.3 对 auto-trace 工作流的验证意义
- 三视图能把一篇系统论文的"论点—机制—证据"闭环在真实 trace 上逐图对应（Fig.2 → 车道图，Fig.6 → 等待/执行比，Fig.10 → MLFQ 账本 Q1–Q4 = 98/96/237/2009、降级 148 次、β 提升 0 次，Fig.12/13 → 尾部收益 > 均值）。
- 对比论文口径：论文 ShareGPT/BFCL 至高 2×、Mixed 高载 5×；本机排队压力处于其低载区间，实测 1.33× 与该负载段两线间距量级一致。
- 边界：效应只在引擎排队时存在；β=2.0 未触发饥饿线（反饥饿是保险不是收益来源）。

## 2. auto-trace：Qwen3.5-27B / DCU 的负载分析与性能 trace

来源：负载分析 [auto_trace/local_reports/workload_profile/index.html](auto_trace/local_reports/workload_profile/index.html)；性能 trace 总入口未打包（`/data3/Projects/auto_trace/local_reports/index.html`）

### 2.1 负载分析（workload_profile，R01→R02→R032→R042 全部 complete）
- 对象：一次真实 eager serving 请求，29 次 forward（6 次 prefill chunk + 23 次 decode），64 层 hybrid decoder（linear_attention + full_attention），vLLM V1 / ROCm-DCU（gfx936）。
- R02 算法 trace 选出 9 个代表 layer 事件（覆盖 initial prefill / cache growth boundary / tail prefill / first decode / late decode × linear/full attention）；R032 固定输入 make_fx 采样；R042 把 1,079 个 FX 节点严格无重叠划分为 **86 个 dependency-ordered process**。
- 每个 process 用中文回答"是什么 / 为什么需要 / 怎么做"，并给出带真实 shape 的张量图（如 full-attention 链：RMSNorm → [4096,5120]×[5120,14336] QKVZ 投影 → GQA6 → gated → [4096,6144]×[6144,5120] 输出投影）。
- 证据边界写清了：固定输入路径的 ATen/custom-op DAG；GDN core、KV-cache mutation、unified attention 内部 kernel 不透明；不含实测延迟或 FLOPs 结论。

### 2.2 性能 trace（perf_trace）
**单 batch**：prefill span 5.69 s / decode span 11.68 s / 请求 17.46 s（eager 插桩观测）。优化落点定位：
- prefill：GQA6 direct（P1、P6）与 page784（P2–P5，784 = 12×64+16）两条 attention 路径；MMAC GEMM M=4096 复用 TunableOp solution。独立 benchmark H11.5 GQA6 相对 R24 的 TTFT 降幅：4–8K 15.89%、8–16K 20.47%、16–32K 24.65%。
- decode：两条专用 GEMV（K5120 gate_up_proj M=34816、17408 CTA × 640 threads 的归约结构）是主要优化落点。

**双卡 Batch8（DP2 / TP1）**：
- 选卡 `score = 4×waiting + running`；本例 4+4，两卡输入 token 85,843 vs 84,781（差 1.24%），八请求在途交集 666 s。
- 每卡独立 continuous batching，观测到 B1→B2→B3→B4 真实演进，kernel 配置随 local B 切换（GQA BM64 → BM16 → BM32 → packed B4）。
- OOM 控制：按最大剩余 prompt 长度分档的 prefill token 预算（>16K: 512 / 8–16K: 1024 / ≤8K: 2048）。

**并发与资源分析（analysis_reports）**——结论是负面的但很重要：
- 19 个同设备 kernel 重叠区间（单 batch 13、Batch8 6），峰值都是 2，但重叠并集只有 µs 级（单 batch 10.96 µs / Batch8 0.42–0.61 µs，对比 busy 并集 1.5–5.8 s）。**峰值 2 ≠ 存在显著并发收益**。
- "现有资源证据可用于定位 GDN 与 RMSNorm 的读写/L2 特征，但不足以给 MLP 定性瓶颈，也不足以证明增加并发就能提速。"
- L2 指标口径：单 batch 只有"重放流量投影到 R07 延迟轴"的吞吐（GB/s），Batch8 恢复了 TCC_HIT/MISS → L2 命中率与请求速率（6912 项核对通过），但没有已验证的 gfx936 L2 峰值，1206 GB/s 是 HBM 实测参考不能用于 L2，因此**不生成 L2 带宽利用率百分比**。

**受控并发采集（2026-09-10，workflow05_r10，15 轮）**：单 Batch / Batch8 / Batch16 × {逐层全插桩、原 dispatcher/FULL graph 对照、Process 门控 L1/L2/HBM 读写、步门控}，30 个页面 file:// 下审计 PASS，覆盖 99.5–99.7%。Batch16：16 请求、4,270 process、4,467,979 kernel。

## 4. 问题与思考

### 4.1 auto-trace：全面但找不到重点
现状：单 batch 329,988 process 实例、Batch8 704,916、Batch16 4.47M kernel；三视图 × 15 轮 × 10 段 × 多资源轨道。报告本身已经做了几层过滤（只保留累计时长占比 >10% 的 process 类型、每宇宙 5 堆对数聚类、全局堆排序、只画有硬件关联的窗口），但读者仍要面对几十个页面才能得到一句结论。

Agentix 那边的对照给了一个提示：**当有一个明确的论点（"收益只来自排序"）时，三视图各自只需要回答一个是/否问题，图就变得可读了**；而 DCU 这边没有预设论点，三视图就退化成了数据陈列。并发报告最后的结论也印证了这一点——它更多是在说"证据不足以下结论"，而不是"发现了 X"。

可能的方向：
- 把"论点先行"做进工作流：每轮采集前先写一个可证伪的假设（例如"decode 阶段 gate_up_proj GEMV 顶着 HBM 墙"），三视图只为该假设选窗口。
- 给高延迟视图加一个"离群 process"层：不是按总时长排堆，而是按"同类 process 的时长分布中偏离中位数最远的实例"排——热点通常是离群，不是最大堆。
- 资源墙的定性需要硬件峰值；DCU 的 L2 峰值没有，先做一个 L2 命中型微基准把基准补上（报告里已经留了输入框但未执行）。

### 4.2 MLX：开发难度大、参考少
- 论文没写的部分目前靠 DFU3500 ref_arch 补（Instance 基址表 ↔ trip/stride、DMA 双缓冲 ↔ cdc_dma），但 RTL 只有单 PE 前端，"周期 = 论文周期"只能靠论文报告的利用率间接检验。目标 3 的主要缺口就是这个。
- 每 CDC 还剩 ≈250 周期暴露量没有归因（DRAM 延迟、Y 回写、单通道带宽），需要逐项加而不是一次调平。
- 三项 ISA/调度候选（跨迭代 load-ahead、exp.acc、累加器末迭代 store）会让 MLX 更快，但只在论文机制要求时采用——否则加速比复现失去意义。

### 4.3 下周计划
1. **Agentix**：把 R10 报告的三视图选材标准（R10_SUMMARY_AUDIT.json）抽成 auto-trace 工作流的"论点驱动选窗"模板，反向用到 DCU 的 Batch8/16 trace 上。
2. **auto-trace**：对 Batch8 Process 门控轮次（cache002 / read003 / write004）做一次"单假设"分析：decode 阶段 gate_up_proj GEMV 的 HBM 读带宽是否接近 1206 GB/s；补 L2 微基准。
3. **MLX**：等 v8 扫描出来重跑 Fig.20/21；开始单 PE RTL 与核心的 load/compute/store 三流水逐周期对照，把 RTL 差异作为误差项进台账。
